# DAO、提案、投票与金库

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：识别治理状态、票权分布与执行权限。

## 先看一个场景

社区要用金库支付一笔开发费。论坛讨论、快照投票、链上多签执行都可能发生，票通过后要核实能否执行和何时生效。

## 核心原理

DAO 将部分协调流程设为公开规则。典型生命周期包含提案、投票、门槛判定、排队、执行和结果复核。

## 需要区分的概念

讨论积累信息；投票机制衡量治理支持；Timelock 延迟执行；金库执行角色负责实际资产变化。

## 对照两种治理结构

| 检查项 | 论坛投票与多签执行 | 链上 Governor 与 Timelock |
| --- | --- | --- |
| 投票凭证 | 签名消息及快照规则 | 治理合约中的投票记录 |
| 提案到执行的关联 | 由多签确认执行内容 | 动作列表进入排队与执行流程 |
| 常见独立权限 | 多签模块、签名门槛 | 提案、取消、执行、管理员角色 |

不论采用哪种机制，都要查看实际执行者是否可以修改内容、金库余额是否充足、是否有紧急角色。将一次投票文本和实际执行回执并排核对，可以识别投票与资产变化之间缺失的证据。

## 从投票结果找到真正的付款

社区提案 G-07 希望向开发团队支付 25 单位。模拟流程中，提案公布金额与收款方，投票达到门槛。通过后进入排队等待，稍后由有权限的地址执行金库付款。我们要分别找三份证据：投票结果、排队动作和实际付款回执。

| 页面状态 | 目前可以说 |
| --- | --- |
| 讨论中 | 社区可以读方案并提出修改 |
| 已通过 | 在指定规则下投票达到要求 |
| 等待执行 | 金库动作已排队，等待条件符合 |
| 已执行 | 查看执行交易及收款方、金额、资产 |
| 执行失败 | 保留回执并查批准的修复路径 |

在真实治理中，论坛投票、链上投票与金库执行的责任可能由不同参与者承担。把「通过了什么」和「最终做成了什么」分开记录，需要读代码时再查提案操作和权限细节。

## 动手练习

为提案记录文本、快照区块、法定人数、通过门槛、调用列表和可取消条件。给执行失败、重复执行和紧急暂停补状态。
