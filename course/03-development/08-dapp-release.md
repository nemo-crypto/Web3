# DApp 发布、监控与重试

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：设计前端交易状态、索引一致性及应急演练。

## 先看一个场景

兑换页面更新后，有用户点完确认却只看到超时提示。团队先要弄清：是页面读不到交易结果，还是交易根本没有提交。这两个情况会给用户不同的下一步。

## 核心原理

发布一套新页面，要能回答它接的是哪条网络、合约地址是什么、怎样读取数据，发生异常时怎么切回旧页面。准备发布记录，把页面版本、网络配置、合约地址和接口描述放在一起，方便恢复后继续检查交易。

## 需要区分的概念

钱包负责征得用户同意，节点提供提交和执行的证据，服务端用证据判断业务状态。页面用来展示这些结果的那份整理数据，工程里常叫**读模型**。它更新得晚时，应给用户看到正在核对，而不是一条模糊的失败提示。

## 以一次钱包余额改版演练发布

团队要把资产页从只显示 ETH 改成同时显示 ETH 与一种代币。新版上架前先用测试配置核对三件事：页面查的是哪条链，代币合约地址是什么，显示金额按多少位小数换算。测试者用两组模拟账号切换，故意让旧请求最后返回，验收它不能覆盖新账号的余额。

| 时机 | 有什么可以核对 |
| --- | --- |
| 发布前 | 旧版与新版配置对照，测试网络、合约、接口与显示精度 |
| 逐步放量 | 观察读取失败比例和交易查不到回执的情况 |
| 发现异常 | 区分前端显示、节点响应和真实链上记录 |
| 恢复 | 站点可以回滚页面代码，已经发生的付款仍需单独追踪 |

先练习准备一份发布表，记录版本、时间、配置和负责人员，再演练 RPC 查询报错。失败记录保留上一次成功结果并告诉用户数据可能旧了，避免用零余额替代未知结果。

## 动手练习

列出链或账号切换、签名拒绝、替换交易、回执失败、RPC 断线和索引延迟。逐项定义 UI 文案、超时、重试与日志。
