# 合约权限、升级与安全验收

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：从防御角度审阅角色、升级、外部调用与应急流程。

## 先看一个场景

小林昨天存了 100 个模拟代币，金库给了他相应份额。今天金库发布新版本，小林打开原来的地址，仍想看到正确余额并按规则提取。这就是一次升级需要保住的用户体验。

## 核心原理

部分合约用固定入口接收请求，再交给可更换的代码执行。固定入口常叫**代理**，运行的代码称为**实现**。升级就是改变之后如何处理请求，同时要确认原来保存的数据仍能被新代码正确读取。

## 需要区分的概念

读项目文档时，按动词查权限：谁能改配置，谁能升级，谁能暂停。**Timelock**是一种等待机制，受约束的动作在等待条件满足后才可执行。每个权限以实际合约配置为准。

## 用一个虚拟金库读懂「升级」

尝试想象用户永远向同一地址存取资产。这个地址可能是代理，负责保持调用入口和状态；实现合约提供运行的业务逻辑。更换代码后，用户还是向旧入口发请求，但系统跑的规则已经变化。做升级评审时，先列出哪些地址变了、谁批准、原数据如何读、普通用户怎样退出。

| 角色或记录 | 新手应该核对 |
| --- | --- |
| 升级者 | 谁能改实现，是否要经团队共签或延时 |
| 暂停者 | 哪些功能可暂停，用户的读取、还款或退出怎样处理 |
| 部署记录 | 原实现、新实现、代理地址和升级交易怎样对应 |
| 用户数据 | 原余额和份额值在升级后是否保持一致 |

不要只看新代码首页上的演示余额。测试先在旧实现中生成真实的本地状态，再升级，并用相同用户读取份额、转账、退出，最后用无权限角色确认不能改变实现。对恢复动作验证入口、审批与回执。

## 动手练习

维护角色表，测试未授权动作被拒绝、旧数据在升级后仍可读、应急暂停解除后可恢复，确认多签和延迟策略。
