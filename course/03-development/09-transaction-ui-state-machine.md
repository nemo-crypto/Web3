# 交易前端状态机 · 从点击到业务完成

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：统一签名、提交、替换、失败与确认时的页面文案和恢复条件。

## 先看一个场景

用户点击「兑换」，停留在钱包授权页，之后又刷新了浏览器。同一时刻，后台拿到原交易被替换的消息。前端需要用可追踪的业务操作恢复进度，并把替换后的哈希用于后续查询。

## 定义页面状态

| 状态 | 推进证据 | 页面行为 |
| --- | --- | --- |
| 待钱包确认 | 已建立请求上下文 | 暂停重复提交，允许取消 |
| 已广播 | 获得网络与交易哈希 | 提供浏览器链接并保留草稿 |
| 执行成功 | 回执成功且业务事件匹配 | 显示实际结果与确认进度 |
| 执行失败 | 回执回退或明确拒绝 | 说明失败现象与可用动作 |
| 确认状态未知 | 连接中断或服务超时 | 查询既有流程，再决定是否重试 |
| 已替换 | 同账户同 nonce 存在替代交易 | 对照实际动作，并更新追踪信息 |

状态机保存操作 ID、网络、账户、请求代次和 TX 哈希。已有外部状态时，恢复逻辑优先查证据，不能只读按钮缓存。收到旧请求的回调先核对操作 ID 与代次。

## 给同一张兑换单写四句页面文案

模拟订单 D42 想以 100 个 A 换 B。钱包尚未签名时记录 D42 与本次请求的代次。提交后保存链、账户和哈希，刷新页面可以恢复查询。用户随后切换地址，旧请求结果仍可记入 D42，但页面不能把旧地址余额刷进当前账户。

| 实际情况 | 页面可以说 | 允许什么动作 |
| --- | --- | --- |
| 在钱包等待 | 请打开钱包确认，站点尚未提交交易 | 查看钱包、取消当前尝试 |
| 有哈希且没有回执 | 已提交，正在等链上执行 | 查看浏览器链接、重新查询 |
| 已执行，业务索引还没更新 | 已收到成功回执，正在核对到账 | 查看回执与进度 |
| 明确收到失败回执 | 兑换未完成，查看已消耗的手续费 | 核对输入后重新报价 |

收到超时错误时先查钱包历史和既有操作，再决定是否重试。显示「状态暂未确认」能帮用户区分正在核对和已经失败。

## 动手练习

画一个兑换状态图，为钱包拒绝、合约回退、回执成功但服务未确认、换账户后旧结果回传各写一条测试。每条测试应能回答「用户是否可以再发起一次」。

## 自测

多个窗口同时点击确认，防止重复广播仅靠禁用按钮是否足够？
