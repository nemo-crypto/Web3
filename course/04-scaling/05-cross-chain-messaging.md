# 跨链消息、IBC 与中继

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：区分资产桥与通用消息的来源验证、顺序和超时。

## 先看一个场景

源链完成资产锁定后发送一条消息，目标链接收证明并更新应用。源链回执和消息完成各有标识。

## 核心原理

跨链消息由发送链提交、传递组件搬运并经目标验证规则认可。验证可依赖轻客户端、签名集合或其他协议机制。

## 需要区分的概念

消息编号处理顺序与去重；验证规则判断源事件可信度；中继负责送达；超时和确认决定失败如何恢复。

## 双链状态机

~~~mermaid
flowchart LR
    A[源链发出] --> B[等待源链确认]
    B --> C[中继递交证明]
    C --> D[目标验证与执行]
    D --> E[登记目标结果]
    C --> F[超时处理]
    D --> G[执行失败待处理]
~~~

| 跨链记录 | 建议字段 |
| --- | --- |
| 来源 | 源链 ID、发送合约、发送交易、消息序号 |
| 送达 | 目标链 ID、验证方式、任务状态 |
| 结果 | 目标交易、执行结果、最终确认、失败原因 |

核对超时后的退款或重试由哪一层执行，特别是资产已经锁定的场景。IBC 的具体客户端、连接和应用处理取决于接入协议，不能从中继者名推断验证规则。

## 把消息和实际送达想成两张证明

小林在链 A 提交一项操作，目标希望链 B 把某笔订单改成「已付款」。源链产生消息 M-8，链 A 查到回执。**中继**负责把消息与验证所需材料带到 B，B 按自己的规则决定承不承认、是否执行。于是「A 已发出」「消息已经送达」「B 实际改了订单」各有一份证据。

| 查 M-8 得到什么 | 能据此说明什么 |
| --- | --- |
| 只有源链回执 | 请求已发起，需要继续跟踪消息 |
| 目标侧已接收但执行回退 | 消息已到，业务动作未完成 |
| 重复递交同一消息 | 先查协议的消息序号和执行记录 |
| 目标执行成功 | 再核对 B 改的是原来指定的订单 |

**IBC**是一类跨链通信规范。具体实现中的连接、数据包、回执和超时，要沿接入协议的规则查。以证据判断状态，可以区分中继暂时不在线和目标业务真的执行失败。

## 动手练习

画出发送、证明、传递、验证、执行和确认六步。针对消息重复、源链重组、目标调用回退分别写状态。
