# SIWE 与后端登录会话

[课程首页](../../README.md) · [本阶段](README.md)

> **学完能做到**：设计钱包登录、会话过期与地址切换后的处理。
>
> **建议先读**：[连接钱包与账户切换](04-connect-wallet.md)。

## 先看一个场景

用户在浏览器连接账户后想进入订单页。服务端根据一次性登录声明验证密钥控制权，建立可撤销的网站会话。

## 核心原理

Sign-In with Ethereum 使用约定的消息格式绑定域、地址、链、Nonce 与时间等字段。登录服务验证消息内容和签名，再存储身份与会话。

## 需要区分的概念

连接发生在客户端；SIWE 签名证明声明所述地址的控制权；后端 session 决定 API 权限；合约钱包签名验证可能依赖 ERC-1271。

## 登录接口设计

| 接口 | 输入 | 服务端动作 |
| --- | --- | --- |
| 获取挑战 | 应用会话、当前地址和网络 | 产生一次性 nonce，设置短有效期，记录挑战归属 |
| 验证签名 | 完整消息、签名 | 核对预期字段和签名，原子消费挑战，建立会话 |
| 读取会话 | 站点会话标识 | 检查失效时间与当前业务权限 |
| 退出 | 当前会话 | 使站点会话失效 |

用户点击钱包拒绝时保留可重试入口。账号切换后，先将已有会话标为待重新验证，禁止使用新地址预览旧地址专属订单。签名挑战只表达登录用途，交易和代币授权分别通过专门入口请求。

## 一份可以读懂的登录挑战

服务端先发出一次性编号。浏览器把站点名、当前地址、链、编号和时效组成待签消息；签完后把原消息和签名交还服务端。服务端校验这些字段，确认签名来自预期账户，随后建立网站会话。下面只是字段示意，实际构造按标准格式。

~~~text
哪个站点        shop.example
要证明的账号    地址 A
哪个网络        示例网络
一次性编号      训练用随机编号
这次做什么      登录以查看订单
~~~

编号在验证成功后应只消费一次。若旧请求被重放、域名不匹配，或用户已切换账号，各自应有明确的错误结果。能打开订单是服务端会话的权限，登录之后要扣款还需要对应的授权与交易。

## 动手练习

客户端请求 nonce；钱包签署完整声明；后端校验域、URI、时效、链和签名；原子消费 nonce；建立会话；切换账户时重新绑定。

## 自测

同一登录签名被重复提交两次，后端如何处理？

<details>
<summary>查看参考答案</summary>

首次成功时将 nonce 标记为已消费，后续请求不再创建新会话。Nonce 消费与会话建立应考虑并发。

</details>
